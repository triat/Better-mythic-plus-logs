# Backend architecture (`src/`)

Read this before changing anything under `src/`. The specs in `docs/superpowers/specs/` are the authority when this page and the code disagree — fix whichever is wrong.

## Data flow of a lookup

```
bmpl lookup / POST /api/lookup
  └─ performLookup(opts, deps)                         src/lookup.ts
       ├─ fetchMplusData → rankings (WCL, ~10 pts)     src/mplus.ts, src/wcl/queries.ts
       ├─ analysis: metric (dps/hps by spec), spec filter, per-dungeon best runs, displayed runs (≤ 9)
       ├─ in parallel:
       │    ├─ enrichRuns → per displayed run: cached RawRunReport or WCL report.table (~10 pts/run)   src/signals/enrich.ts, wcl-run.ts
       │    └─ fetchRioProfile → Raider.IO (free, 1 h TTL cache, retry/backoff)                        src/signals/rio-client.ts, rio-profile.ts
       ├─ summary (cross-run aggregates, peers medians)                                                src/signals/summary.ts, peers.ts
       ├─ attachDeepdive → cached deep-dive analyses only (0 pts)                                      src/deepdive/attach.ts
       └─ evaluate(payload, cfg) → axes + verdict                                                      src/evaluation/
  └─ buildLookupPayload(...) → LookupPayload (the one type the CLI renderer and the web front consume)
```

`Deps` (`store`, `gql`, `fetchFn`, `evalConfig`, `tables`) exist so tests inject fakes — keep every new I/O behind them. `LookupPayload = ReturnType<typeof buildLookupPayload>`: add fields there, never in a parallel type.

## WCL client and budget

- `src/wcl/auth.ts` caches one OAuth2 client-credentials token in memory; `src/wcl/client.ts` `gql<T>(query, variables)` is the only network entry point; `src/wcl/queries.ts` holds every GraphQL document — every query selects `RATE_LIMIT` (`rateLimitData { limitPerHour pointsSpentThisHour pointsResetIn }`; `PING_QUERY` reads it alone for 0 pts), including `buildMultiEncounterQuery` in `src/mplus.ts`. `gql()` hands `json.data` to `observeRateLimit`, which forwards to whatever `setRateLimitObserver(fn)` installed — only `createHostedRuntime` (`src/hosted/runtime.ts`) installs one, so the CLI and local mode never account anything.
- Budget: 3600 pts/h per API client. Costs: rankings ≈ 10, one run's `report.table` enrichment ≈ 10, one deep-dive run ≈ 3, Raider.IO 0. Nothing may fetch outside `lookup`/`mplus` enrichment and the explicit deep-dive. The deep-dive refuses with 402 when fewer than 20 pts remain and measures `pointsSpent` against a PING baseline.
- Never add a per-death, per-event or per-page query pattern; batch into one request per run (see `REPORT_DEEPDIVE_QUERY`).
- **Hosted budget and per-member quotas** (issue #5): `src/wcl/meter.ts`'s `PointsMeter` turns `rateLimitData` deltas into spend. `run(userId, fn)` (`AsyncLocalStorage`) attributes the WCL calls made inside `fn` to `userId`; `observe(rl)` compares a response's `pointsSpentThisHour` against the previous observation of the same WCL window — a new window opens only when the estimated `windowEnd` has passed *and* the counter dropped (otherwise, whatever the clock says, it's an in-window delta and `windowEnd` is refreshed from that response); a lower counter before `windowEnd` charges 0 and does not lower the baseline; a computed delta above `MAX_CHARGE_PER_OBSERVATION` (100) is treated as a clock-boundary artefact and re-primes the baseline instead of charging; the first observation only primes it (charged to nobody, which is why `instance.pointsSpentThisHour` in `GET /api/admin/usage` can exceed the sum of `users` by roughly one call) — rounds to 0.1 pt, charges the running request via `charge()` and upserts into `usage_hourly` through the `UsageSink`; `wrap(gql)` returns a `gql` wrapped to call `observe` on every response. Constants `ESTIMATE_RANKINGS = 10`, `ESTIMATE_RUN = 10`, `ESTIMATE_DEEPDIVE = 3` are checked *before* spending (WCL only reports the cost after). Attribution is exact when a user's calls do not overlap another's and approximate under concurrency (a delta lands on whichever request observed it); the hour's total in `usage_hourly` is always exact.
  `src/hosted/quota.ts`'s `QuotaGate.reserve(user, estimate)` returns `null` (go ahead, nothing spent either way) or a `QuotaRefusal { error: "quota" | "budget", message, used, limit, resetInS }`: `"quota"` when a non-admin's `used + estimate` would exceed `BMPL_POINTS_PER_USER_HOUR` (`HostedDb.usage`, calendar-hour buckets via `hourStart()`/`HOUR_MS` in `src/hosted/db.ts`); `"budget"` for anyone — admins included — when the meter's last snapshot is still in-window and `limitPerHour − pointsSpentThisHour − estimate` would fall under `POINTS_FLOOR = 100`, the floor that keeps the shared client's cached-data paths alive for everyone. `status(user)` reports `{ used, limit (null for admins), resetInS }`; `QuotaGate.for(user)` binds a `Reserve = (estimate) => QuotaRefusal | null` for one request.
  `deps.reserve` is consulted in two places in `performLookup` (`src/lookup.ts`): `ESTIMATE_RANKINGS` before the rankings fetch, then `uncachedDisplayedRuns × ESTIMATE_RUN` before enrichment — a refusal returns `{ ok: false, status: 429, error, quota }` before that phase's fetch runs. `runDeepdive` (`src/deepdive/run.ts`) consults `deps.reserve` for `ESTIMATE_DEEPDIVE` right after the cache check and before the PING, alongside the existing `MIN_BUDGET_POINTS = 20` pre-check. `runLookupWithCache` (`src/server/lookup.ts`) checks history *before* any of this (a cache hit never consults the gate) and de-duplicates identical concurrent lookups into one in-flight `performLookup`; a `refresh` never joins a flight and only registers one when none is already in progress for that key. `src/server.ts` wraps every hosted handler in `runtime.meter.run(ctx.user?.id ?? null, …)` so attribution covers the whole request. `GET /api/admin/usage` (admin-only) reports `{ ok, hourStart, resetInS, limitPerUser, instance: RateLimitSnapshot | null, users: [{ userId, discordId, username, role, points }], hours: [{ hourStart, points }] }` — `users` is the current hour, `hours` the last 24 buckets ascending, `instance` null until the process's first WCL call.

## SQLite cache — `src/signals/store.ts`

`Store` interface (`openStore(path)`, `openStoreOrMemory`, `getStore()` singleton, `closeStore()`), tables created with `CREATE TABLE IF NOT EXISTS`, schema changes must be additive:

| Table | Key | Content | Lifetime |
|---|---|---|---|
| `wcl_run_raw` | `(report_code, fight_id)` | raw WCL run report, `QUERY_VERSION = 2` | forever (immutable) |
| `wcl_deepdive` | `(report_code, fight_id, character)` | Casts + Buffs tables + filtered cast events, `DEEPDIVE_QUERY_VERSION = 1` | forever |
| `rio_profile` | `(region, realm, name)` | raw Raider.IO profile | `RIO_TTL_MS` = 1 h |
| `users` | `id` | hosted-mode Discord identity + role | until removed |
| `sessions` | `id` | hosted-mode login session | 30 d sliding, purged hourly |
| `invites` | `discord_id` | hosted-mode allow-list entry | until removed |
| `user_history` | `(user_id, key)` | hosted-mode lookup history, one row per tab, raw payload | 20 per user, oldest evicted |
| `user_history_auto` | `(user_id, alias_key)` | hosted-mode auto-level alias | with its entry |
| `user_settings` | `user_id` | hosted-mode "your key" + legend state | until removed |
| `usage_hourly` | `(user_id, hour_start)` | hosted-mode WCL points per member per calendar hour | forever (small) |
| `defensives_shared` | `(key, id)` | hosted-mode approved override entry | until replaced |
| `defensives_proposals` | `id` | hosted-mode correction proposal (pending/approved/rejected) | forever |
| `audit_log` | `id` | hosted-mode audit row (login, admin action, quota refusal, rate limit / origin rejection, WCL/server error) | `AUDIT_RETENTION_MS` = 90 d, purged hourly |

Bump a `*_QUERY_VERSION` when the GraphQL document changes shape; old rows are then ignored and refetched. Rankings are never cached (they move). The `_db` handle is for tests only. Path: `BMPL_DB_PATH` or `bmpl.db` next to `.env`.

## Evaluation — `src/evaluation/`

Six axes (`survival, utility, throughput, consistency, preparation, experience`), each a weighted mean of sub-signals scored through piecewise-linear curves (`curve.ts`), weights per role (`dps | healer | tank`, `src/roles.ts`). Rules live in `default-config.json` (`levelScale`, `expectedIlvl` per season, `axes.*.subSignals.*.{curve, weights}`, `confidence: { high, medium, consistencyMinRuns, deepdiveMinRuns }`); the user may override with `evaluation.json` next to `.env` (`config.ts` merges and validates). `evaluate()` returns `Evaluation { axes, global, verdict: invite|maybe|pass|insufficient, confidence, runsUsed, analyzedRuns, … }` with `Evidence[]` per axis — every score must be explainable by evidence lines; the front shows them verbatim. A sub-signal with no data is `null`, never 0. `bmpl evaluate saved.json` replays the model offline on a `lookup --json` payload — use it when tuning curves.

## Signals — `src/signals/`

`wcl-run.ts` parses a raw run report into `RunSignals` (deaths, interrupts, dispels, avoidable damage, ilvl, timed/depleted). Peer comparison (`peers.ts`) uses the medians of the other players in the same run, same role. Kicks are normalised by spec cooldown (`kick-cooldowns.ts`); dispel capability per spec (`dispel-capability.ts`). Avoidable damage = a per-dungeon spell list under `avoidable/season-*.json`, regenerated with `just import-avoidable` from the upstream postmortem project (attribution issue pending upstream — do not redistribute the list elsewhere). Previous-season Raider.IO absence is *unknown*, never penalised.

## Deep-dive — `src/deepdive/`

Defensive-cooldown analysis of one run for one character, on demand (`bmpl analyze`, `POST /api/deepdive`). Spec: `docs/superpowers/specs/2026-09-16-run-deep-dive-design.md` — its rules (capacity, usage, inclusive/half-open windows, verdict precedence, wipes excluded, stale-table ids never judged) are encoded in `analyze.ts` tests; change the spec and the tests together or not at all.

- `defensives.json`: shipped table `{ version, denylist, specs: { "Class:Spec": [{ id, name, cooldownS, durationS, kind: major|minor|immunity }] } }`. Validate with `just audit-defensives` (empirical, ~9 pts per spec per run; `--shared` audits the hosted approved layer instead of the local file) rather than from memory; Wowhead pages cannot tell talent-tree membership.
- `table.ts` merges shipped ⊕ override into a `LoadedTables` (`shipped`, `override`, `source`, `overridePath`); `LoadedTables.source` is `"file"` locally (the override is `defensives.json` next to `.env`, edited through `POST /api/defensives` or by hand) and `"shared"` in hosted mode. Every effective entry carries an `EntryOrigin` (`"shipped" | "override" | "shared" | "pending"`). Three pure helpers both loaders build on: `mergeEntry(list, patch)` folds one patch into an override list (`ignore` replaces any earlier patch for the id, otherwise fields merge over it), `layerPatches(base, patches, origin)` applies several patches over a base override and tags them, `tagOrigin(override, origin)` tags a whole override. An invalid override file is reported as `tableWarning`, never silently dropped.
- **Hosted shared layer and proposals** (`src/hosted/defensives.ts`, issue #6): `tablesFor(repo, userId)` returns shipped ⊕ `defensives_shared` (the admin-approved layer) ⊕, when `userId` is given, that member's own pending rows from `defensives_proposals` tagged `origin: "pending"`. `propose(repo, user, className, spec, patch, now)` validates the patch against the caller's own effective table (an unknown id must be complete), then either records a `pending` row for a member — a second proposal on the same key/spell merges into the existing pending one — or, for an admin, writes `defensives_shared` and records the proposal `approved` at once; both paths run inside `repo.transaction`. `decide(repo, id, admin, status, note, now)` approves (upserts into `defensives_shared`) or rejects (the `note` stays on the row, visible to its author) a pending proposal, also transactionally. `tablesOf(ctx, runtime)` (`src/server/deepdive.ts`) is the one place any handler gets a `LoadedTables` — the member's tables when hosted, the file otherwise. Hosted `POST /api/lookup` and history reads always call `withCachedAnalyses(payload, tables)` to re-attach analyses against the *requester's* tables on every read, so an approval needs no history iteration, and a member who joins another member's cached lookup (the shared-history copy in `src/hosted/history.ts`) never sees that other member's pending layer, only their own. Admin moderation: `GET /api/admin/proposals?status=pending|approved|rejected` (rows include `username`), `POST /api/admin/proposals/:id/approve|reject { note? }`.
- The audit of unlisted self-cast buffs uses `denylist` + the `NON_DEFENSIVE_NAME` regex; add ids to the denylist rather than widening the regex when a single spell is wrong.

## Server — `src/server.ts`

`Bun.serve` on `:3000`, composed in `src/server.ts` from `src/server/*`: `routes.ts` (route table, first match wins, `Route["method"]` includes `GET | POST | PUT`), `routes-shared.ts` (both modes: `/api/lookup`, `/api/deepdive`, `/api/defensives` GET/POST, `/api/history[/…]`, `/api/events` SSE, `/api/status`, `/api/health`), `routes-local.ts` (local mode only: `/api/setup` writes `.env`, `/api/watch/{start,stop,status}` clipboard watcher, `/api/quit`), `routes-user.ts` (`GET/PUT /api/settings`, hosted only — 404 in local mode), `lookup.ts` (`runLookupWithCache(opts, history)` + `historyOf(ctx)`), `deepdive.ts` (analysis + table handlers; `withCachedAnalyses(payload)` attaches today's cached analyses on a hosted read, 0 pts; `refreshLocalHistory()` re-runs after `POST /api/deepdive`/`POST /api/defensives` in local mode only), `sse.ts` (clients keyed by user id: `broadcast` reaches only local, user-less clients, `broadcastTo(userId, …)` is the hosted fan-out, plus heartbeat — no hosted code emits events yet, since the clipboard watcher is local-only, so a hosted member's stream carries only the initial status and heartbeats until a later issue adds hosted events), `watcher.ts`, `http.ts` (`jsonResponse`), `validate.ts` (see "Hardening" below), `security.ts` (hosted headers/CSP). Everything not routed serves the embedded `web/dist` (`src/web-static.ts`, `src/web-assets.ts` — guarded dynamic import, 503 when not built). Responses are `jsonResponse({ ok, … })`; errors carry `{ ok: false, error }` with 4xx/5xx. `runServer({ port, open, hosted, hostedConfig, fetchFn, assets })`: in hosted mode the local routes are not registered, `open` is ignored and every response gets the security headers. `routes-auth.ts` (`/auth/discord`, callback, `POST /auth/logout`, `GET /api/me`) and `routes-admin.ts` (`/api/admin/*`, `auth: "admin"`) are registered only in hosted mode; every `Route` carries `auth: public | user | admin`, enforced by `authGate` in `src/hosted/auth.ts` after `resolveRequest` turns the `bmpl_session` cookie into a `RequestContext { hosted, user, sessionId, ip, now, history }` handed to every handler — `history` is `localHistory` (`src/server/local-history.ts`, the local-mode singleton) locally, the signed-in user's store when hosted, `null` when anonymous. Both are `HistoryStore` implementations (`src/server-history.ts`: the interface plus `HistoryListItem`, and `History`, the in-memory one used locally); the hosted one is `openUserHistory(db, max).forUser(userId)` (`src/hosted/history.ts`), backed by the `user_history`/`user_history_auto` tables, capped at `HISTORY_MAX_PER_USER = 20`; its sharing rule is that another user's entry for the same key younger than `SHARED_HISTORY_TTL_MS` (6 h) is copied into the caller's history as a cache hit, unless the caller's own entry exists or the lookup is a `refresh`. `src/hosted/runtime.ts` (`createHostedRuntime`) builds the `HostedRuntime` (`config`, `db`, `states`, `fetchFn`, `secure`) once per server and owns the hourly session-purge timer, so `routes-auth.ts`/`routes-admin.ts` import the type from there rather than from `server.ts`. **Admin page routes** (issue #8, `routes-admin.ts`, all `auth: "admin"`, 0 WCL pts — SQLite and the meter's last snapshot only): `GET /api/admin/invites` now resolves each invite to the user it became (`user: { id, username } | null`); `GET /api/admin/proposals` joins each proposal against the spec's current effective entry (`current`, plus `ignored`) so the page can render a from → to diff; `GET /api/admin/users` (and the role-change response) carry `pointsHour`, `points24h`, `sessions`, `configAdmin` per user; `POST /api/admin/users/:id/sessions/revoke` deletes that user's sessions (`{ ok, sessionsEnded }`; 400 on your own id — "Sign out instead"); `GET /api/admin/instance` reports `{ version, uptimeS, dbPath, dbBytes, lastBackupAt, env }`. `src/hosted/instance.ts` builds `env`: `describeConfig(config, wcl)` lists the effective `.env.hosted.example` variables in file order and masks every secret — a secret's *value* never leaves the server, only whether it is set (`"•••• (set)"` / `"(not set)"`), the session secret shows its byte length, and `WCL_CLIENT_ID` (not secret, but not to be pasted into a screenshot either) is abbreviated to `first4…last4`; `lastBackupAt(dir)` is the mtime of a `last-backup` file next to `.env` (written by the deploy, issue #10), `null` when absent. Hosted tables (`users`, `sessions`, `invites`, `user_history`, `user_history_auto`, `user_settings`) live in the same SQLite file through `src/hosted/db.ts` (`openHosted(store._db)`, exposing `HostedDb.history` and `HostedDb.settings { get, update }`); sessions are 30-day sliding, purged hourly; OAuth `state` is single-use and bound to the `bmpl_oauth` cookie (`src/hosted/oauth-state.ts`).

### Hardening (issue #9)

`respond()` in `src/server.ts` runs every request through, in order: static file → route lookup → Origin check (hosted, non-GET/HEAD only, before the auth gate) → `authGate` → in-app rate limit → `audit.scope(...)` + `meter.run(...)` → the handler. Any step that refuses returns before the next one runs, so e.g. a rejected Origin never reaches the auth gate and an unauthenticated request never reaches the rate limiter (a rate-limit key needs the resolved user).

- **`src/server/validate.ts`**: one validator for every JSON body, in both modes. `obj({...})` builds a `Schema<T>` from `str`/`int`/`num`/`bool`/`oneOf`/`opt`/`nullable`; `parseBody(req, schema, emptyAs?)` reads and parses the body. Unknown fields are refused (`Unexpected field \`x\``), numbers are finite, integers where the domain is integer (`fightID`: no NaN/float/string), strings pattern- and length-bounded (`WOW_NAME`, `WOW_REALM`). Every route's body schema is exported from this file (`LOOKUP_BODY`, `DEEPDIVE_BODY`, `DEFENSIVES_BODY`, `SETTINGS_BODY`, `INVITE_BODY`, `NOTE_BODY`, `ROLE_BODY`, `SETUP_BODY`, `WATCH_BODY`) — **every JSON body goes through `parseBody`; add a schema in `src/server/validate.ts`, never call `req.json()` directly in a route.**
- **`src/hosted/origin.ts`** (`checkOrigin(headers, baseUrl)`): hosted-only CSRF guard on every non-GET/HEAD request. A present `Origin` that doesn't match `BMPL_BASE_URL`'s origin (including the literal `null`), or a `Sec-Fetch-Site` of `cross-site`/`same-site`, is refused with 403 `{ ok:false, error:"Cross-site request refused" }` and an `origin_rejected` audit row; a request with neither header passes (non-browser clients — a browser always sends at least one on a cross-site request).
- **`src/hosted/ratelimit.ts`** (`RateLimiter`, sliding window of hit timestamps per key): `DEFAULT_RATE_LIMITS` are `/auth/*` 10/min per IP, `POST /api/lookup` 30/min per user, `POST /api/deepdive` 60/min per user. A refusal answers 429 with an integer `Retry-After` (≥ 1 s) and records `rate_limited`; the limiter runs after the auth gate and before the handler, so an invalid body still counts against the limit. `ServeOptions.rateLimits` (`Partial<RateLimits>`) is the test hook to shrink the windows.
- **`src/hosted/audit.ts`** (`AuditLog`, `AsyncLocalStorage`-scoped): `record(action, entry?)` inserts one row, never throws (a logging failure must not fail the request), and fills `userId`/`ip`/`target` from the request's `scope()` when the caller doesn't pass them explicitly. Actions: `login`, `login_denied`, `logout`, `invite_add`, `invite_remove`, `role_change`, `sessions_revoke`, `proposal_approve`, `proposal_reject`, `quota_refused`, `rate_limited`, `origin_rejected`, `wcl_error`, `server_error` — each maps to one `AuditKind` (`login | admin | quota | security | error`) via `ACTION_KIND`/`kindOf`/`actionsOf`. Free-text fields are clipped (`clip`, 300 chars default) before they reach a row — never secrets, cookies or full WCL bodies. `AUDIT_RETENTION_MS` is 90 days; `src/hosted/runtime.ts`'s hourly purge calls `db.audit.purgeBefore(now - AUDIT_RETENTION_MS)` alongside the session purge. `GET /api/admin/audit?kind=&before=&limit=` (`routes-admin.ts`, `auth: "admin"`) returns `{ ok, rows, counts, errors24h, nextBefore }` — `counts`/`errors24h` are always over the full table (not the filtered page), keyset-paged by `id` (`before`), newest first.
- **`src/wcl/client.ts`**'s `WclError` (`kind: "http" | "graphql" | "nodata"`, `status`, `publicMessage` clipped to 200 chars) is thrown by `gql()` on every WCL failure; `setWclErrorObserver(fn)` lets hosted mode's runtime install a hook that records `wcl_error` — local mode and the CLI never install one, so a `WclError` there is a plain thrown error with no audit side effect.
- **Sanitising rule**: `failureBody()` in `src/server/deepdive.ts` decides what a failure response's `error` field says. Local mode always keeps the original message. Hosted: a WCL failure (`r.wcl` set) shows as `WCL: <publicMessage>` — the member's own report is considered actionable — any other 5xx becomes the bare `Internal error`, and every other 4xx keeps its message (validation errors, quota, rate limit, origin). An uncaught exception in a handler is caught in `respond()`'s `catch`, logged to stderr and as a clipped `server_error` audit row, and answered as `Internal error` regardless of what the exception said — no stack trace, path or `Error.message` ever reaches a hosted client.
- **`src/hosted/config.ts`**'s `weakSecret(s)` refuses a `BMPL_SESSION_SECRET` that is a known placeholder or has too little character variety, in addition to the existing ≥32-byte length check; `validateHostedEnv()` reports it the same way as a missing variable (exit code 2 with the fix message).

## CLI — `src/cli.ts`

Commands: `ping, char, lookup, mplus, evaluate, analyze, defensives, serve, invite, watch, zones, raw-rankings, raw-encounter, help`. Rendering in `format-mplus.ts` (picocolors). Anything that spends points must confirm unless `--yes`; `--json` never bypasses the confirmation. `if (import.meta.main) main()` keeps the module importable by tests. `serve --hosted` (or `BMPL_MODE=hosted`) goes through `planServe()`: pure argument/env resolution, `resolveMode()` then `validateHostedEnv()` (`src/hosted/config.ts`) — on a missing or invalid `BMPL_*` variable the command prints the list and exits 2 without starting the server.

## Config and files next to `.env`

`resolveEnvPath()` looks in cwd then next to the executable. Beside that `.env`: `bmpl.db`, `evaluation.json`, `defensives.json`. Env overrides: `BMPL_DB_PATH`, `BMPL_EVAL_CONFIG`, `BMPL_DEFENSIVES`, `WCL_CLIENT_ID`, `WCL_CLIENT_SECRET`. All are user data: git-ignored or, at the repo root, simply never staged.

Hosted mode (`bmpl serve --hosted`) additionally requires `BMPL_BASE_URL`, `BMPL_SESSION_SECRET`, `BMPL_DISCORD_CLIENT_ID`, `BMPL_DISCORD_CLIENT_SECRET`, `BMPL_ADMIN_DISCORD_IDS`, `WCL_CLIENT_ID`, `WCL_CLIENT_SECRET` — see `.env.hosted.example` and the README's "Hosted mode" section.

## Invariants worth re-reading before a change

- Immutable raw in, recomputed analysis out. Never cache a derived score.
- A missing signal is `null` with a reason, not 0.
- Costs are stated in the README "API cost" section; update it when a query changes.
- Season-specific content is a versioned data file, not code.
- `Class:Spec` keys, WCL spelling, everywhere.
- Hosted payloads are stored raw and get today's analyses attached on read (0 pts); nothing iterates other users' rows after an analysis.
- A quota refusal happens before the WCL step it guards and that step spends nothing; the lookup's enrichment gate sits after the rankings query, so a lookup refused there has already paid ~10 pts. Cached data never consults the gate.
- The CLI and local mode never install the observer: no accounting, no quota.
- Hosted mode never reads or writes the server's `defensives.json`; the approved layer is `defensives_shared`.
- A proposal is validated against its author's effective table (unknown ids must be complete).
